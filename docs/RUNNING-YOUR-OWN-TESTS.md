# Running your own tests on the branch

This is the path for testing the `transform-latency-instrumentation` broker
branch ([vuldin/redpanda](https://github.com/vuldin/redpanda)) with your own
changes, guests or test plans, unattended, without leaving a cluster billing.

The short version:

```bash
cp wb.local.env.example wb.local.env    # your AWS profile, key, checkouts
aws sso login --profile <yours>
scripts/offline-gate.sh                 # every free check, incl. a local broker SIGKILL test
scripts/autorun.sh check plans/smoke.plan
scripts/autorun.sh start plans/smoke.plan
scripts/autorun.sh status               # or: tail -f results/run-*/autorun.log
```

`start` returns immediately. The run provisions a cluster (with Prometheus
and Grafana), runs the plan, fetches results, exports the scraped metrics,
writes `RESULTS.md`, tears down and verifies the teardown through the EC2 API
on its own, with an independent watchdog that does the same at the deadline
even if the run process has died.

Everything lands in `results/run-<date>-<plan>/`:

| file | what |
|---|---|
| `RESULTS.md` | the tables, generated by `scripts/summarize-run.py` from the raw files; excluded trials flagged |
| `STATUS.md` | phases, outcomes, timings, teardown verdict, cluster lifetime |
| `metrics-bundle/` | the Prometheus data for every measured window; `docker compose up -d` inside it, then http://localhost:3000 ([Looking at a finished run](#looking-at-a-finished-run)) |
| `client-results/`, `<phase OUT>/` | the runners' raw output: loadgen reports, verdicts, guest logs, placement |
| `autorun.log`, `<phase>.log`, `teardown.log` | what happened |

## What is on the branch

Beyond upstream `dev`, the branch carries (each commit builds standalone; see
`scripts/verify-each-commit.sh`):

- the in-broker **relay**: transform output pushed straight to in-broker
  consumers, no Kafka fetch, plus per-stage latency histograms
  (`relay_stage_metrics_enabled`) - see [RELAY-LATENCY-STAGES.md](RELAY-LATENCY-STAGES.md)
- **trusted modules** (`wasm_trusted_modules`, keyed by the binary's sha256)
  granting capabilities: `shared_memory`, `network`, `relay_consumer`
- **guest-state persistence**: a trusted guest registers a shared-memory
  region; the broker checkpoints it every 5s into the input partition's raft
  group and writes it back before the first record after a restart.
  `require_state_recovery` (admin-API deploy only) makes a restore failure
  fatal instead of silently starting empty
- **graceful leadership transfer** (`data_transforms_graceful_transfer_timeout_ms`):
  drain, commit and checkpoint together before a leadership move. **Off by
  default** - see "What we know" below
- per-phase startup histograms (`transform_startup_latency_seconds` and friends)

## One-time setup

1. **Three checkouts.** This repo; [redpanda-wasm-clients](https://github.com/vuldin/redpanda-wasm-clients)
   (the guests); the broker branch. Build the broker with the capped bazel
   command in [SETUP.md](SETUP.md#a-redpanda-binary-built-from-the-branch)
   (`-c opt --jobs=6 --local_resources=memory=16384`; uncapped builds have
   exhausted workstation memory). Build the guests with `make build-wasm`.
2. **`wb.local.env`.** Copy `wb.local.env.example` and set your AWS profile,
   EC2 keypair and checkout paths. It is gitignored; `wb`, `autorun.sh` and
   `offline-gate.sh` all read it, and anything in your environment wins.
3. **`scripts/wb doctor`** checks tools, the AWS session, keys, the local
   broker build and the guest artifacts.

## The offline gate

`scripts/offline-gate.sh` runs everything that costs nothing: the guests' Rust
tests (including a 200k-operation differential test of the order book), the
wasm build with the published-module checksums, `go vet`/`go test`, the bench
shell suites, a syntax check of every script and plan, and
`bench/local-rehearsal.sh` - one broker from your build, a snapshotting guest,
traffic, sentinel orders, SIGKILL, restart, and a check that the book came
back - and `bench/local-relay-delivery.sh`, which runs the e2 harness on one
local broker with `RELAY_DELIVERY=precommit` and then `committed` and checks
that both deliver every record and that committed waits for the output write
(it is measurably slower on the relay hop; a broker without the option
measures the same in both). It records the commits of all three repos in
`results/GATE-PASSED`.

Before the first run of a new or changed plan, `bench/local-plan-smoke.sh
plans/<plan>.plan` runs each distinct `run e2` phase of it, scaled down, on a
local broker (about 1-2 minutes per phase). It catches settings that do not
work together before a cluster is paid for; `run traditional` and
`run durability` phases need cluster hosts and are listed as not covered.

`autorun.sh start` refuses to provision unless the gate passed for exactly the
commits you are running, and refuses uncommitted bench changes. Commit first,
then gate, then start. `REHEARSAL=0` skips both local broker tests when the
broker has not changed; don't skip it after broker changes - it is the check
that found snapshot persistence silently not working in a real broker.

## Plans

A plan is a small bash file in `plans/`:

```bash
TOPOLOGY=six-broker      # or single-az, multi-az, highcore (terraform/*.tfvars)
DEPLOY_ARGS=(-e transform_memory_limit=16777216 -e transform_snapshot_max_size=16777216)

phase NAME EST_MINUTES <wb arguments...>
phase depth 10 run e2 MODE=bookdepth GUEST=book-matcher 'BOOKDEPTH_LEVELS=0 1000'
phase kill  35 run durability ACTIONS=kill 'DEPTHS=1000 10000' OUT=@RUN_DIR@/kill
```

- Each phase is one `wb` invocation. Quote a `KEY=VALUE` whose value has
  spaces. `@RUN_DIR@` becomes the run's directory.
- Estimates matter: a phase starts only if it fits before the teardown
  reserve, and is killed at 1.5x its estimate. `autorun.sh check PLAN` prints
  the phases and whether the total fits the cap.
- Between phases the cluster is reset (transforms and test topics deleted,
  maintenance cleared, balancers and graceful-transfer back to defaults, every
  broker started). A failed phase is retried once.

Shipped plans:

| plan | what | phases | cluster |
|---|---|---|---|
| `smoke.plan` | proves your build, keys and account end to end | ~22 min | 3 brokers |
| `published.plan` | the published in-broker vs external comparison (REPRODUCE.md) and the resilience series | ~145 min | 3 brokers + 8 clients |
| `resilience.plan` | the resilience series on its own: maintenance mode and leadership transfer, graceful drain unset vs set, then the module-residency A/B ([RESILIENCE.md](RESILIENCE.md)) | ~90 min | 3 brokers + 8 clients |
| `book-durability.plan` | the 2026-10-15 book-depth + durability suite | ~171 min | 6 brokers |
| `production-shape.plan` | the in-broker matcher against external, co-located and co-located-on-isolated-cores deployments with the same production-shaped book and order flow; long windows for p99.99; rate with that book; kills with the victim held down | ~107 min | 6 brokers |
| `relay-modes.plan` | what waiting for the output quorum costs in-broker consumers: `RELAY_DELIVERY=precommit` vs `committed`, interleaved, at fan-out 1 and 20 | ~30 min | 6 brokers |
| `state-and-jitter.plan` | snapshot cost full vs live; graceful moves with the live region; every deployment on one cluster with 90s windows (p99.99 for each); the transforms scheduler share A/B; tail against rate | ~3.6h | 6 brokers |
| `checkpoint-ab.plan` | the broker's guest-state checkpoint inline (original) vs background, interleaved, with the live region at depth 1,000 and 10,000 | ~49 min | 6 brokers |
| `checkpoint-chunks.plan` | whether splitting the checkpoint into chunks (64 KiB, 16 KiB) or checkpointing every 30s instead of 5s removes the depth-10,000 stall; plus a partition scale-out sweep (1-8 partitions at 120k and 240k orders/sec) and the committed relay at fan-out 50 | ~2 h | 6 brokers |

`smoke`, `published` and `book-durability`, one after the other, is the full
set (`published` already includes the resilience series). They use different
topologies, so they are separate runs; each provisions and tears down its own
cluster and writes to its own run directory - no run's results, logs or
metrics ever overwrite another's. `published.plan` has not yet been run end to end through
autorun; `wb reproduce`, which it wraps, is the path every published number
came from.

A plan can define `pre_up() { ...; }` for steps that must happen before
provisioning (`published.plan` sizes the client fleet and picks a region
there); if it fails, nothing is provisioned. A plan without one gets
`scripts/select-region.sh` run for its topology instead, so a run never
inherits the region an earlier run chose; `REGIONS` (exported by the plan or
set in the environment) is the preference order. Plans can also `export`
settings for runners that read the environment (`wb reproduce` does), and
refer to `$RUN_DIR`.

### Run modes and knobs

| | |
|---|---|
| `autorun.sh start PLAN` | provision, run, tear down |
| `autorun.sh start --existing PLAN` | run on a cluster you brought up with `wb up` / `wb deploy` (keeps an armed watchdog for that RUN_DIR) |
| `CAP_HOURS` (none) | optional wall-clock cap. By default a run takes as long as its plan takes; the only deadline is your AWS credentials' expiry minus the reserve (teardown needs live credentials), and `start` refuses a plan they cannot cover - log in again, or set `ALLOW_SHORT_RUN=1` to run what fits |
| `RESERVE_MIN` (25) | time held back for fetch, archive, teardown, verify |
| `KEEP_CLUSTER=1` | skip the end-of-run teardown to keep iterating; the watchdog still tears down at the deadline |
| `EXPORT_RESERVE_S` (900), `EXPORT_MIN_S` (600), `EXPORT_MAX_S` (3600) | the end-of-run metrics export gets the time left before the deadline less `EXPORT_RESERVE_S`, clamped to [min, max]; a full-scope dump runs ~50s per measured window |
| `EXPORT_PARALLEL` (4) | measured windows dumped at once on the monitoring host; a 56-window run needs ~50 min one at a time, ~13 at 4 |
| `RUN_DIR`, `ARCHIVE_DIR` | where results go; ARCHIVE_DIR also gets a sha256-checked tarball. Set ARCHIVE_DIR once in `wb.local.env` to archive every run |

Credentials: the run exports your role credentials once at start, so it
survives the SSO token expiring; the role credentials' own expiry (often 8-12h
after login) is the real limit, and `start` refuses a plan they cannot cover.
A fresh `aws sso login` does not always renew them: the AWS CLI keeps serving
cached role credentials from `~/.aws/cli/cache` until those expire. Check
before starting:

```bash
aws configure export-credentials --format env | grep EXPIRATION   # add --profile <your-profile> if you use one
```

If the expiry did not move after a login, delete the cached role-credentials
file in `~/.aws/cli/cache` and check again; the next call fetches new ones.

## Watching a run, and keeping the metrics

Every topology provisions a monitoring host (Prometheus + Grafana, node_exporter
everywhere) before anything is deployed. Once the cluster is ready the run logs

```
WATCH: Grafana http://<ip>:3000 (anonymous viewer; admin/wasmbench to edit)
```

and `scripts/autorun.sh status` shows it. Start with the **overview**
dashboard; its last row is for stateful transforms (snapshot restore time,
dark time across leadership moves, recovery failures). The other two are relay
stages and measurement health. What each panel reads, and the gates that must
be zero, are in [MONITORING.md](MONITORING.md).

- The security group admits only the address that ran `wb up`, so a colleague
  can watch their own run but a link will not open for anyone else - export
  and share the bundle instead.
- The scrape is for watching. Every number in `RESULTS.md` comes from
  loadgen's own histograms and the runners' verdicts, not from Prometheus.
- Before teardown the run calls `wb monitor export <run-dir>`: the measured
  windows (when the loadgen scrape target was up, padded 30s) become finished
  TSDB blocks plus a Grafana with the same dashboards. Afterwards:
  `cd results/run-.../metrics-bundle && docker compose up -d`, then
  http://localhost:3000 ([Looking at a finished run](#looking-at-a-finished-run)).
- Running by hand instead of through autorun: `wb monitor` (URL and
  reachability), `wb monitor export <results-dir>` before `wb teardown`.

## Looking at a finished run

The cluster's Prometheus and Grafana are gone after teardown. What survives is
`metrics-bundle/` in the run directory: every measured window as Prometheus
blocks, plus a Grafana with the same dashboards, set to the recording's time
range. It needs Docker with Compose v2 and nothing else - no cluster, no AWS,
no copy of this repo (so it can be zipped and sent to someone).

```bash
cd results/run-<date>-<time>-<plan>/metrics-bundle
docker compose up -d          # Prometheus on :9090, Grafana on :3000
# open http://localhost:3000  - anonymous viewer, opens on the overview
./validate.sh                 # optional: every panel query returns data
docker compose down           # stop it (the data stays)
```

What you see:

- Shading on every graph: one region per autorun phase (hover for plan,
  phase, attempt and outcome). Two more layers are off by default, because
  each sits inside a phase and overlapping layers blur the boundaries: the
  exported windows, and - for runs whose loadgen publishes its stage -
  loadgen's measured windows per level. Their toggles are at the top of the
  dashboard.
- The "now running" strip names the phase at the END of the selected range,
  so zooming to a stretch of the run tells you what was running there.
- Latency panels open on "latency samples: measured only": the samples the
  published numbers come from, without each level's preload and warmup spike
  (which also flattened the y-axis). Switch to "all" to see those. Bundles of
  older runs get the loadgen stages this needs from their phase logs, via
  `scripts/bundle-add-phases.sh`.
- Only the measured windows were exported (padded 30s), so the gaps between
  them are empty by design: they were provisioning, deploys and settling.

From an archived copy (`ARCHIVE_DIR`): check and unpack the tarball first, then
use the `metrics-bundle/` inside it the same way.

```bash
cd <archive-dir> && sha256sum -c run-<...>.tar.gz.sha256 && tar xzf run-<...>.tar.gz
```

Things that trip people up:

- Use `up -d`. A plain `docker compose up` stays attached to the containers'
  logs, which are quiet once both are up, so it looks hung when it is serving;
  if the bundle was already running it only attaches. Ctrl-C there stops it.
  `docker compose ps` shows whether it is running.
- One bundle at a time: they all use ports 3000 and 9090, so
  `docker compose down` the previous one first.
- Prometheus reads the blocks only at startup. After adding blocks (below),
  `docker compose down` and `up -d` again, and reload the browser tab: an open
  tab keeps the dashboard it loaded. Refreshed dashboards alone are picked up
  by a running Grafana within ~10s.
- A bundle exported before 2026-10-16 has no phase or window shading (the
  phases were never in its data, and its window annotation never worked). Add
  both, and refresh its dashboards to the current ones:

  ```bash
  scripts/bundle-add-phases.sh results/run-<date>-<time>-<plan>   # bundle stopped
  ```

  It builds the phases from the run's `autorun.log` with the bundle's own
  Prometheus image, and is safe to re-run. It changes the copy you point it
  at, not the archived tarball.

## The runners a phase can call

- **`run e2`** (on client0) - steady-state latency and cost sweeps; modes and
  their contracts are in [TESTS.md](TESTS.md). For stateful guests:
  `GUEST=book-matcher`, `STATE=off|snapshot`, `SNAPSHOT_EVERY_MS`,
  `CANCEL_FRACTION` (share of input records that are cancels, with as many
  passive inserts), `MODE=bookdepth` with `BOOKDEPTH_LEVELS`.
  `SNAPSHOT_MODE=live|full` (with `STATE=snapshot`): `live`, the default,
  keeps the region current after every record and registers only what is in
  use; `full` re-serialises the whole book every `SNAPSHOT_EVERY_MS`, the
  original format. `TRANSFORM_SHARES=<n>` sets
  `data_transforms_scheduling_group_shares` for the run and restores it;
  `CHECKPOINT_INLINE=true|false` does the same for
  `data_transforms_state_checkpoint_inline` (true: the original checkpoint
  that blocks the transform loop and forces a flush; false: background).
  `CHECKPOINT_INTERVAL_MS=<ms>` sets `data_transforms_state_checkpoint_interval_ms`
  (minimum time between checkpoints, broker default 5000) and
  `CHECKPOINT_CHUNK_BYTES=<n>` sets `data_transforms_state_checkpoint_chunk_bytes`
  (split a larger checkpoint into records of at most n bytes, replicated one
  after another; 0, the default, writes one record). Both need a broker that
  has them, and both are recorded in the fingerprint.
  `TIMELINE_MS` (500) gives every report a per-interval timeline so a stall
  can be placed in time. Each level's RESULTS.md row splits the end-to-end
  p99.99 into the produce leg and the in-broker relay leg, and its
  `stalls>3ms` column counts timeline buckets whose slowest sample took over
  3ms, adding the period when they recur at a fixed spacing (`23 @ 5,000ms`
  is a stall on every 5s checkpoint).
  `RELAY_DELIVERY=precommit|committed` (needs a broker with the option) sets
  when in-broker relay consumers get the producer's output: before its
  durable write (default) or after a quorum has acknowledged it. It is set on
  the producing transform and recorded in the report fingerprint.
- **`run durability`** (from your machine, because a kill needs ssh to the
  leader) - per trial: fresh topics, deploy book-matcher, traffic over a
  preloaded book, sentinel orders in waves at T-10/-6/-3/-1/-0.3s, the action
  at T, recovery, then a read-back of the book. Knobs: `ACTIONS`
  (`maintenance transfer kill`), `DEPTHS`, `TRIALS`, `STATE`, `GRACEFUL_MS`,
  `REPLAY=1` (rebuild the same book by replaying the topic from the start and
  time it), `PER_WAVE`, `WAVES`, `KILL_DOWN_S`, `KILL_MODE` (`down`: the
  victim is held down for `KILL_DOWN_S` so a replica must take over;
  `systemd`: the unit's `Restart=` brings it straight back, as in
  production), `RATE`, `ORDERS_PER_RECORD`,
  `CANCEL_FRACTION`, `OUT`.
- **`run resilience`** - latency during leadership movement; see
  [RESILIENCE.md](RESILIENCE.md).

Every durability trial line says whether traffic spanned T and whether
leadership actually moved. A trial that says `LEADERSHIP-DID-NOT-MOVE` tested
nothing; exclude it.

## Testing your own guest

- Build it in redpanda-wasm-clients; add it to `make build-wasm`,
  `scripts/deploy-wasm-cluster.sh`'s staging list and the ship list in
  `ansible/deploy-wasm.yaml` (they must agree, or the deploy fails mid-way).
- A guest importing `redpanda_wasm_shared_memory` does not instantiate unless
  its sha256 is trusted with `shared_memory`. Deploy it with
  `scripts/deploy-transform.sh`, which trusts it (read-merge of
  `wasm_trusted_modules`), retries across brokers, and can set
  `--require-state-recovery` and `--from-start`. Stock `rpk transform deploy`
  can do neither.
- Register the region in `main`, before the first record; the broker restores
  into it before delivering one. Write the region only at the end of an
  invocation (the broker reads it between invocations), and carry a checksum:
  the region is opaque bytes to the broker.
- Guests cannot see input offsets, so replay detection after a restore has to
  come from something in the records. `rust/src/bin/book-matcher.rs` shows one
  way (per-producer sequence lanes) and logs `STATE restored|gap|stats` lines
  to the transform log topic, which the durability runner collects.
- Size the region to what is in use. Each checkpoint (every 5s) copies the
  whole registered region, not just what you wrote, and replicates it through
  the input partition's raft group; restore scales the same way. Register only
  the bytes in use and register again as the state grows - a new registration
  replaces the old one. book-matcher's `SNAPSHOT_MODE=live` does this and keeps
  the region current after every record, so nothing is ever re-serialised. The
  region must fit within `data_transforms_state_snapshot_max_size` (4 MiB by
  default, 64 KiB-64 MiB; plans raise it with `-e transform_snapshot_max_size`)
  and the guest's memory limit (`-e transform_memory_limit`); both are applied
  at deploy and need the broker restart the deploy does.
- No snapshot means an empty restart, not a replay. Without a restored region,
  a restarted transform resumes from its committed offset with nothing in it.
  Rebuilding state from the topic takes a fresh deploy with
  `scripts/deploy-transform.sh --from-start`, which is what `REPLAY=1` times.
- The in-broker relay never leaves the node: each input partition and its
  relay consumer's partition must be led from the same broker, or the relay
  delivers nothing (the e2 pre-check reports PRECHECK-FAILED). With more
  brokers than RF, two single-partition topics can get replica sets that share
  no broker; the harness then moves replicas before transferring leadership
  (`colocate_leadership` in `bench/lib-cluster.sh`). A runner of your own
  should do the same, or create the output topic with the input topic's
  replica assignment.

## What we know so far

Results are not checked in; each finding below names the plan that produces
it, so you can regenerate the tables (RESULTS.md in that plan's run directory).

- The depth-tolerant book holds 10,000 resting orders per side at the same
  latency as an empty book (~500us p50, ~1ms p99.9 at 30k orders/sec); the
  reference sorted-Vec book saturates by 1,000 (`book-durability.plan`).
- On one cluster with the same book and order flow, in-broker execution has
  the lowest p50 and the lowest p99.99 of every deployment at fan-out 1-50:
  ~440-520us and 1.6-3.2ms, against 1.3-3.0ms and 4.0-7.8ms for an external
  client and 0.9-2.3ms and 2.7-9.6ms co-located on the broker host. Most of
  the in-broker tail is the client's `acks=all` produce; the relay to
  in-broker consumers adds 0.4-0.6ms at p99.99, halved by
  `data_transforms_scheduling_group_shares=1000` (`state-and-jitter.plan`).
- One partition's clean ceiling with a 1,000-deep book is 60-90k orders/sec
  (`state-and-jitter.plan`, rate phase).
- With the broker default (graceful transfer off), planned moves lose state
  like crashes. With `data_transforms_graceful_transfer_timeout_ms=5000` and
  book-matcher's live region, every move restored every acknowledged order
  (`book-durability.plan`, `state-and-jitter.plan`).
- A broker kill can lose the last few seconds: the snapshot (5s) and the
  committed offset (3s) are independent, so the loss depends on where the
  kill lands - some trials lose nothing, others the last 1-3s. With the dead
  broker held down, a transform runs again on a surviving replica in ~1s
  (`production-shape.plan`, `KILL_MODE=down`).
- With the live region, state costs nothing at depth 1,000 (p99.9 ~1ms, as
  with no state); at 10,000 the broker's checkpoint still adds ~3ms at p99.9
  (`state-and-jitter.plan`). It is a stall on every 5s checkpoint, on the
  produce leg, and replicating the checkpoint in the background does not
  remove it (`checkpoint-ab.plan`): the ~2 MB region goes through the input
  partition's own raft log as one entry, so produces queue behind it.
  `checkpoint-chunks.plan` tests splitting it.

## Gotchas that have cost real runs

- `wb run` returns the remote runner's exit code, so a failed phase is
  retried and recorded as failed - but a level can still be unclean with rc 0.
  Read RESULTS.md's clean column, not only the phase outcome.
- Don't rebuild the broker in `REDPANDA_SRC` while a run is in progress. Every
  `wb run` phase checks that each broker runs exactly your local build (the
  binary gate) and refuses to measure otherwise, so a mid-run rebuild fails
  every later phase. Build in a separate checkout (`git worktree add`) or wait.
- A p99.99 needs at least 100,000 samples; RESULTS.md prints n/a below that.
  30-second windows only support p99.9, so compare tails only between arms
  measured with windows of similar length.
- Durability trials are bimodal (see "What we know"): run several and report
  the distribution, never a single trial.
- Admin API calls that act on a partition must reach its leader:
  `transfer_leadership` sent elsewhere without following redirects silently
  does nothing. Deploys can return 503 `Leader not available` from a
  non-leader broker; retry elsewhere.
- Backgrounding over ssh: `ssh host "cd x && nohup cmd &"` keeps the ssh
  channel open until `cmd` exits (the backgrounded list still holds stdout).
  Redirect the shell's fds first, as `run-durability.sh`'s `CBG` does.
- Never edit a script in place while a run is executing it - bash reads
  scripts incrementally. Write a copy and `mv` it over.
- Teardown destroys the monitoring host, which holds the only copy of the
  scraped metrics. autorun exports first; by hand, run
  `wb monitor export <results-dir>` before `wb teardown`.
- Read [METHODOLOGY.md](METHODOLOGY.md) before quoting any number.

## Changing the bench

- Every fix or new test lands in the repo as a script, plan or gate step, with
  the docs updated in the same change. One-off scripts and hand-written plans
  under `results/` do not count.
- Nothing committed may assume one machine: no home paths, key names, AWS
  profiles or account ids. Settings go through `scripts/lib-env.sh` and
  `wb.local.env`. Check a change from a fresh clone with no `wb.local.env`
  (for example `env -i HOME=<empty dir> PATH=$PATH scripts/wb doctor`).
- Never commit built binaries, and keep third-party and customer names out of
  files and commit messages.
- New or changed plan: run `bench/local-plan-smoke.sh plans/<plan>.plan`
  before paying for a cluster, then the offline gate.
